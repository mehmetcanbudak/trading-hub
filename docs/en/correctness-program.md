# Memoshi correctness program

The approved work protects order admission, research results and saved work. The candidate is `fix/memoshi-correctness`, based on `1310f0a1fcee0b04ae6aabfbb19bf906699b3366`. Its baseline runtime matches the accepted `5c2583c` installation. This candidate has not replaced that installation or merged into `memoshi`.

The canonical checkout, personal data, credentials, upstream checkpoint, historical English audit baseline and Rust/Swift pins were not changed.

## Attention

- The pending-peer Accounts Close timeout was a production race. The close loop could declare cancellations complete just before an equivalent session's awaited pending send was acknowledged, and the send slot then refused the close. CI captured that refusal with isolated fake URIs. When nothing has been committed or sent, the close now returns to cancellation within its existing 15-second bound. The captured-finality refusal for a reappearing replay-absent order is unchanged.
- The other two earlier timeouts most likely came from shared fake-venue authority. Each fake server used a random loopback port without a path, so independent fakes on one port looked like one Rithmic account. Stopped sessions with open orders stay registered by design. An instrumented root-URI suite counted up to 43 such authorities and an expected 0.18 colliding fake starts per run, mostly in Accounts Close tests. A collision leaves a foreign working order that can never become terminal, so the close waits past the 8-second test deadline. Real-session controls reproduce the interference, and per-instance fake URIs remove it: an instrumented isolated run had zero inherited sessions across 116 fakes.
- Retained stopped sessions have a production consequence that needs an owner decision. If a working order ends at the exchange while a connection is stopped, and the same account reconnects in the same process, Accounts Close for that contract keeps refusing until restart. It never sends a wrong order, but it blocks the emergency close.
- The journal consumer now samples corrected data immediately and observes the genuine timer until Statistics displays the same result. A controlled run observed 500 then 400 without reselection. No production timer or financial assertion changed.
- Earlier independent reviews used separate GPT 6.1 Sol contexts. A later Claude review read the native close, admission, durable close journal, quantity caps and live launch code and found only the retained-session consequence above. Remaining files were not re-reviewed across families.
- The `kvp-performance` scene ran three alternating times on the base `1310f0a` and the candidate builds. Every scope's in-process warmed medians overlap, for example a cold chart frame of 41 to 48 ms in both builds, so no regression or speedup is claimed. Wall time was not compared because the base binaries ran from an external disk image. Resource checks are not a physical-disk throughput or GPU claim.
- Automated language-candidate detection is not a natural-language proof. Browser inspection found and fixed one hard-coded Spanish heading after the automated gate passed. All four final English exports retain their loaded charts, and the three ordinary-containing reports now show the English profitability heading.
- Marksman's earlier four warnings most likely came from the editor integration, which indexes the session's main checkout and rejects this worktree as a workspace. Run directly on this tree, it reported 157 ambiguous links and 2 broken links. The Spanish and English guides share file names, and Marksman matches bare names across folders. Same-folder links now use `./`, and the two links into a separate Errata repository are plain text. Marksman now reports zero findings, with a deliberate broken-link control still detected.
- Windows CI exposed four recurring and two intermittent failures, four of which also fail on `memoshi`. Fixture cleanup deleted directory junctions with recursive delete, which .NET routes through `DeleteVolumeMountPoint`. Tick tests read a live day with a stricter share mode than production readers. Ledger fixtures deleted storage while execution projection still held it open. Without `.gitattributes`, Windows checkouts compiled C# raw strings with CRLF, which also breaks catalog lookup of multi-line text; C# sources are now LF everywhere. A macOS CI chart scene read the strategy overlay before its timer redraw.
- A captured-finality test held native admission inside its permission barrier while waiting for a late fill. The close polls every 20 ms and can enter that barrier before the fake's trailing cancel notification is handled. That handler then waits on the held gate, and the fill queues behind it on the same connection until the barrier expires. Delaying the trailing notification into the barrier window reproduced it 3 of 3 times. The test now settles the cancellation before the close, and the same forced interleaving passes 3 of 3 with every original assertion unchanged. Production holds this gate only for the in-memory admission check.
- An ARM64 cleanup failure came from the Rithmic read loop. Its last order notification commits the strategy ledger synchronously, sometimes within 10 ms of the test returning, so Windows refused the temporary-directory delete. A ledger-access probe recorded the same 11 writes before and after the fix. The same race produced macOS "Directory not empty" failures in `RithmicTests`. The closing-quantity test and `NativeOrderTestFixture` now join each Rithmic session with `StopAsync` before deleting storage, which covers every broker the fixture creates.
- Five Binance tests failed intermittently in CI, including on `memoshi` itself. Four are now attributed and fixed: three by #7 and one on `fix/executing-exit-resize`. One remains unattributed.
  - `Triggered_partial_market_stop_remains_current_while_sibling_capacity_reconciles` exposed a production ordering defect. `PollLoop` read open orders before the position, so a fill between the two reads produced a position ahead of its working orders, and the bracket manager cancelled the executing MARKET child. A new hook that fills between the reads fails 3 of 3 runs without the fix. The poll now reads the position first, which matches the bracket manager's stated assumption, and a failed position read still lets the order refresh apply fills and deferred cancels before the error is reported.
    A second interleaving remained in the bracket manager, used by every broker. `Sync` reads exit fills before the live position, so a position report that led a triggered stop's fill shrank the stop, and the next pass subtracted the same fill again. The stop reached 0 and `ReconcileExits` cancelled its executing child. Tracing captured that cancel in the CI assertion's failing run. A fill on a triggered stop's executing child (`ExecutingStopChild`) now never reduces the stop below that order's unfilled quantity. Plain stops keep the full decrement, so a broker without native reduce-only still cancels an oversized remainder. A bracket-level test fails at `HEAD` for amending and non-amending accounts, and a second test keeps the plain-stop cancel.
  - `Runner_public_reprice_market_successor_survives_partial_execution` exposed a second production defect. A runner reprice could cancel a stop that had just triggered; the refused algo cancel was then retried against the executing MARKET child. A new deterministic test fails 3 of 3 runs without the fix. A cancel requested for an own conditional stop now finishes as past cancel once the stop has triggered. Manual stop-limits, later explicit cancels and Cancel all still cancel the triggered order.
  - `A_Modify_whose_cancel_cannot_be_confirmed_reports_the_lost_order_as_rejected` waited only for the Failed state, not the error published with it. It now waits for both.
  - `Recovered_replacement_projects_parent_plus_child_native_quantity_before_held_price_history` had two races in the test. A history request still in flight from the disposed first broker could trigger the recovered test's hook before the recovered broker existed. Tracing caught this, with the hook entered 12 ms before the broker was created, and the test now reproduces it by delivering that request late. The test also read the opening's native identity before the broker set it. The test now waits for the readiness and identity it consumes, its assertions are unchanged, and production code did not change. It passed 200 of 200 runs, including under load. `Unknown_submission_replay_books_each_owned_fill_and_realized_profit_once` did not fail in 50 local runs, so no cause is claimed.
  - Independent review found three pre-existing bracket risks. The first is now fixed on `fix/executing-exit-resize`. When a position report led a triggered stop child's fills, `ReconcileExits` resized the child from a stale fill count, and the replacement cancelled or shrank the order closing the position. Bracket tests reproduced this for both account kinds, failing 3 of 3 runs. Reconciliation now never reduces an executing stop child while the position is same-side and non-zero. Increases still amend, and an explicit cancel, close or flip ends the exemption. Only Binance futures, Bybit and Replay produce executing children, and all three are reduce-only in code; whether the venues cap an oversized reduce-only order at the position is [INFERENCE], not verified live. Stress testing then exposed a third cancel path. The poll thread applied an execution in the middle of a bracket sync, and reconciliation read the stale stop size as a request to enlarge the child; Binance's replace then cancelled it. A tracing run captured this, and a deterministic test fails 3 of 3 runs without the fix. Reconciliation now skips an exit whose executed quantity is ahead of its booked fills, and the same sync loop books the fill first. After both fixes, the original Binance test passed 25 of 25 runs under CPU load. Two pre-existing risks remain for an owner decision, neither reproduced. Bybit shows conditional stops as `Stop`, so the double-counted fill can still cancel a triggered Bybit stop. A Binance fill observed while a replacement is in flight still takes the full decrement.
- On macOS, the `safety` scene's `Delete data: ⌘Enter confirms and deletes the fixture day` failed 0.38 s into its second attempt. The scene started the Data page's asynchronous history scan and only waited for the fixture symbol to appear. On the second attempt that symbol was already listed, so the scan's later `ApplyIndex` rebuilt the lists and dropped the day selection, and Delete found nothing to delete. The scene now awaits the page's own refresh task before selecting. Its checks are unchanged [INFERENCE: from the source and the CI timing; 3 local runs passed].
- On Windows, `kvp-authoring` looked up a newly written indicator immediately after `CompileAll`. `CompileAll` defers publication when the source monitor has already observed a newer folder version, so the lookup could run before the monitor's compile [INFERENCE: Windows watcher timing, not reproduced on macOS's polling monitor]. The scene now waits for the catalog publication it consumes.
- On Windows, four `marked-portfolio-report` checks read an empty executive summary. The scene's section helper required `"Executive summary\n"`, but Windows Markdown uses `\r\n`. It now normalizes line endings like the scene's other helpers; the report itself was correct.
- `BybitAccountIdentityTests.Initial_physical_admission_failure_retries_the_same_observation_after_storage_recovers` failed when run alone because of the test, not the product. The live runner captures xUnit's synchronization context when constructed and posts the retained observation to it; alone, nothing drained that context. The test now uses the queued synchronization context the other runner tests use and drains it, and passes 3 of 3 runs alone.
- On ARM64, `Repricing_an_unowned_manual_opening_reserves_the_opposite_side_bounded_emergency_exit` waited on a count of active Rithmic orders that could still include the rejected order. It now waits for the manual opening itself to be active.
- On ARM64, `Terminal_late_quantity_after_handle_fold_preserves_combined_emergency_reduction_capacity` failed deleting the ownership journal's `.lease` file. The journal holds that file open with no sharing during each write, under a named mutex, and Windows refuses to delete an open file. The test's fault injection now takes the same mutex before replacing the lease [INFERENCE: from the source and the CI error; macOS permits the delete, so it was not reproduced locally].
- On macOS, `kvp-providers` read wallet cards after a fixed 1.05 s pump that relies on the Accounts view's 1 s timer. The scene now waits for the rendered cards before its unchanged check [INFERENCE: the single failure was not reproduced locally].
- On macOS, `account-journal-revision` read chart trade marks after a fixed 0.6 s pump, but TradingView publishes them only on every 15th tick. The scene now waits up to 30 s for the marks, as it already did for statistics, and its value checks are unchanged [INFERENCE: 5 local runs under CPU load passed with and without the wait].
- On ARM64, `WindowsIntegrationTests.PromptStdin_PreservesUnicodeWhitespaceAndShellCharactersWithoutAddingANewline` timed out once after 15 s while Windows PowerShell had not drained a 40 KB stdin prompt. It did not fail in the 17 earlier failed runs, and no cause is claimed, so its deadline is unchanged.
- On macOS, `LiveLedgerConfirmedCostsTests.A_late_subscription_cannot_readmit_a_deleted_owner_but_a_fresh_generation_can_book` read the ledger before its fill was booked. `AccountExecutionProjector.Synchronize()` returns at once when a pass is already running, and the late owner's retirement had queued one. Holding that queued pass reproduced Position 0 (1 of 1). Unforced, it failed 1 of 1,600 runs. The test now waits for its own subscription's update, which is published after the durable ledger write. The forced interleaving and 1,600 further runs then passed, and the assertions are unchanged.
- On ARM64, `BybitAccountIdentityTests.A_recovering_reader_or_native_quantity_append_delivers_the_actual_head_to_foreign_live_risk` read the resumed runner's fees before the recovered fee correction arrived. Recovery publishes the head to a thread-pool financial drain, and `Synchronize()` returns at once while that drain is in flight. Holding the drain open reproduced Fees 0.1 for both cases. Unforced, it failed 4 of 300 runs under load. The test now waits for the drawdown stop that the delivered head triggers, and its assertions are unchanged.
- An independent review of the send-slot retry found no double send, over-quantity or unauthorized cancel. It did find that a refused-then-retried close kept «no close was sent» in `LastError` beside a live close. That is fixed: the refusal is cleared only when the same intent later commits, and a new regression fails without the fix.
- The Windows `safety` scene failed its REAL Cancel and quantity-cap checks because the fake Rithmic venue enforced one session per user and plant across systems. The scene keeps the practice session that still owns unresolved exposure while a `Rithmic 01` session replaces it. A login probe showed the REAL login closing the practice order and PnL plants, and the Windows capture showed the REAL order plant reconnecting. The fake now replaces only a session on the same system [INFERENCE: separate Rithmic systems accept concurrent logins]. The same probe then recorded no cross-system kicks. Production code did not change for this fix.
- The bulk ledger recovery timeout is a test budget, not a hang or regression. Run directly with data on the internal disk, the child recovers 512 heads in 19.4 to 23.9 s on the base and 16.2 to 17.4 s on the candidate, mostly durable admission and reset recovery. Suite load on this Mac and hosted ARM64 runners pushed it past the shared 30-second watchdog. Only that test's snapshot phase now allows 120 seconds; startup, exit and pipe-drain keep the 30-second deadlock watchdog.
- Native Rithmic evidence does not establish exchange-atomic position/fill inclusion, venue-command acknowledgment correlation, server-enforced reduce-only, native OCO or exactly-once delivery. The in-process amendment revision is not a persisted cross-process clock.
- Real local storage failures and a failed archive command remain in the evidence. All eight temporary generated roots were restored as verified current real directories. English, safety and saved-report consumers passed from those paths. Only the owned RAM device was retired after exact runtime and fixture preservation. No personal stores or installed app were used to recover space.

## Pstack choices that changed the work

| Principle | Specific choice |
|---|---|
| Model the Domain | Kept compiled generations, unknown evidence, marked coverage, native row identity and prepared versus committed amendments as distinct data. |
| Foundational Thinking | Named the accounting and ownership shapes before changing their consumers. |
| Boundary Discipline | Kept real provider admission and durable ownership checks at their consuming boundaries. Separated business refusal from actual I/O failure. |
| Type System Discipline | Used explicit nullable evidence and one captured amendment quantity pair instead of interpreting unknown as zero. |
| Laziness Protocol | Reused existing gates and records. Removed the preparation-relative revision and redundant commitment Boolean instead of adding another manager. |
| Build the Lever | Kept rerunnable native regressions, exact source-fingerprint export, strict catalog checks and compiled-registry consumers. |
| Separate Before Serializing Shared State | Used isolated worktrees, fresh stores and one stable authority per fake venue instead of clearing shared execution state. |
| Make Operations Idempotent | Retained durable uncertainty and original identities. Unknown submissions are not automatically resent. |
| Migrate Callers Then Delete Legacy APIs | Migrated consumers to the selected contracts without retaining weaker aliases or alternate dispatch paths. |
| Exhaust the Design Space | Compared independent close-settlement and amendment-provenance designs before selecting the smaller local model. |
| Attack the Premise | Reproduced both precommit publication schedules rather than assuming a committed Boolean or a later callback was sufficient. |
| Fix Root Causes | Fixed causal accounting, captured compilation and leased ownership at their producers and consumers, not with output guards. |
| Test Behavior, Not Implementation | Required real frames, exact persisted money and lineage, later usable operations and restart. Removed diagnostic-word and forwarding pins. |
| Prove It Works | Exercised actual consumers. Builds, source reviews and older green runs did not substitute for final behavior. |
| Sequence Work into Verifiable Units | Kept before failures, individual repairs and complete integration gates separately evidenced. |
| Explain the Number | Kept measured resource results separate from an unestablished comparative benchmark. |
| Guard the Context Window | Partitioned source and evidence reviews while retaining one integration owner and exact file decisions. |

For future work, give pstack one outcome, its consumer-visible acceptance and explicit safety boundaries. Use `how` for ownership walkthroughs, bounded `swarm` audits for independent read sets, `architect` before cross-boundary changes, the Bug fix playbook for executable defects and `show-me-your-work` for resumable evidence. Keep concurrent code owners away from the same execution state.
