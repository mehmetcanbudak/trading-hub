It started as `fix/memoshi-correctness`, based on `1310f0a1fcee0b04ae6aabfbb19bf906699b3366`, and is now merged into `memoshi` through #6 and #7 (`45e68fe`) and #8 (`fd2ff2e`). ## Storage durability

Before this change, journaling was process-crash consistent: execution journals, order ownership and ledger intents were flushed, but runner, portfolio, settings and workspace state was rewritten in place, and Bybit order, alert and replay state was renamed without synchronizing its directory. Every safety-critical state writer now uses one helper, `TradingHub.Common.DurableFile`:

- **Whole-file state** (order ownership including bounded closes, Bybit order state, connection profiles and the isolated credential file, alerts, settings, workspace and drawings, runner/portfolio/proposal state, ledger authorities, storage-location control files, replay results): unique same-directory temporary, one drive flush, atomic rename, then parent-directory synchronization before acknowledgment.
- **Append journals** (account executions, live-ledger records after their published write-ahead intent): a drive flush after each committed record; the directory is synchronized once a new name appears. Existing leases and write-ahead ordering are unchanged.
- **Relocation:** copied files are flushed, and every staged directory and the destination parent are synchronized before the location authority switches.
- `StorageSync.Flush` now issues exactly one drive flush on macOS. .NET 10's `Flush(true)` already sends `F_FULLFSYNC`, so the previous `Flush(true)` plus explicit `F_FULLFSYNC` paid for two drive cache flushes.
- **Windows rename:** `MoveFileEx` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH` (extended-length paths beyond `MAX_PATH`), so the rename is flushed before it returns. Other platforms use `File.Move` followed by the directory sync.
- **Directories:** every directory a writer creates is persisted in its parent before the first durable write inside it is acknowledged. An existing directory that this process has not yet confirmed, for example one left by a process that crashed between creation and synchronization, has its parent synchronized once per process.
- **Visible failures:** alert persistence status includes the underlying cause, redacted against confirmed notification credentials. Failing live runner/portfolio state saves keep retrying, expose `LiveStore.StateSaveError`, and on each new failure episode write a structured warning log and raise a local-only system alert.

**Guarantee:** on macOS/Linux, acknowledged state is designed to survive power loss on storage that honors drive-flush requests. An interrupted write leaves the previous complete file plus an ignored `*.tmp`. Windows flushes files with `FlushFileBuffers` and renames write-through. It has no directory-handle synchronization, so a newly created directory's name relies on NTFS metadata journaling. The Windows branch is unit-tested through an injected native mover on macOS; the Windows CI jobs exercise it natively. Failures propagate or block new exposure as before; for example, an unsynchronized Bybit save refuses the create before transport. Market-data caches are out of scope.

**Evidence:** `DurableStateWriterTests` uses the injected `DurabilityOperations` seam to prove file flush before rename and directory sync after rename for each writer. Its simulated power cuts undo unsynchronized renames, leave truncated or complete temporaries and lose unsynchronized journal names, and recovery reads the previous committed state without phantom intents or orders. No physical power-cut test was performed, and drive or firmware behavior is not certified.

**Measured latency** (internal Apple SSD, 200 samples after 10 warmups, `DurabilityLatencyBenchmark`; machine shared with concurrent agents). Medians in milliseconds:

| Writer | Before (one run) | After (three runs) |
|---|---|---|
| `AccountJournal.Add` | 4.05 | 4.03 to 4.06 |
| `OrderContext.Prepare` (durable intent) | 10.89 | 9.94 to 11.33 |
| `LiveStore.AppendFill` (WAL and record) | 13.76 | 10.29 to 11.12; one contended run 32.4 |
| Append with explicit flush plus directory sync | 7.90 | 4.03 to 4.07 |

A single drive flush dominates, at about 4 ms. A directory sync on APFS costs less than run-to-run noise. Order-path latency did not rise, so no fsync batching was introduced. Settings, workspace, drawings and runner/portfolio saves now cost one drive flush each, where they previously had none. Workspace and drawings skip rewriting content that this process has already committed.

## Order lanes and UI-thread holds

Every manual order gesture (chart and DOM drags, stop/target drops, chart-menu bracket actions, Chart Trader, DOM and hotkey buttons, Bybit Cancel/Close in Accounts) called its account on the Avalonia UI thread. The account call waits for the durable ownership journal (`DurableFile`, one drive flush per record), so a slow disk froze the window for the whole write.

- **Order lanes.** Accounts marked `IThreadSafeOrderEntry` (Binance, Bybit, Rithmic, Tradovate) run each confirmed gesture's account call, unchanged, on `OrderActionLanes`: one first-in-first-out lane per `OrderContext`, after the confirmation dialog and permission checks. The result or exception returns to the awaiting UI code. The status bar shows `<gesture>: pending…` while the call runs and `· N order action(s) pending` while later gestures wait. The result always replaces the pending line: the account's message, the gesture's label when the message is empty, `<gesture>: error after submission; check orders and position: …` when the call throws (written to the crash log as well; the call may have sent an order before failing), and the error the account reported for that call, read inside the lane before a later queued gesture can clear it (safety scene: `order gestures always report their outcome`). A finished entry leaves the pending set before its caller resumes, so its own result is not counted as pending.
- **Accounts page in the same lane.** Accounts Cancel/Close on Rithmic (`Session.CancelAsync`, `Broker.ClosePositionAsync`) and Tradovate (`CancelAsync`, `LiquidateAsync`) start in the account's lane, as Bybit's already did, then await the task they started. A close issued after a queued chart buy therefore starts only after the buy's account call returned (`AccountsOrderLaneTests`).
- **Send turns.** The lane orders only the account call; Tradovate and Binance send the request later from a background task, and separate HTTP connections can reorder requests in flight. `NativeSendTurns` gives each native Tradovate account (in `TradovateTradingSession`, shared by every instrument and the Accounts page) and each Binance broker a first-in-first-out send turn. A request takes its turn synchronously where it is issued (Tradovate single and OCO placements, amendments, cancels, liquidations; Binance submits, replacements, cancels, cancel-all) and is sent only after every earlier request's reply, refusal or failure. New-exposure placements, entry amendments and Reverse wait without a bound (cancelled with their broker); reducing requests (reduce-only or protective orders and their amendments, cancels, closes) wait at most 10 s, then send anyway and report `NativeSendTurns.UnsettledMessage`. An amendment that cannot be sent yet releases its turn while it waits for its order, so it never holds later requests. Forcing tests hold the venue's reply to the earlier buy: `NativeSendOrderTests` (chart buy then Close position, Tradovate and Binance) and the Tradovate Accounts test (buy, then Accounts cancel and close, arrival order asserted unsorted) all saw the later requests arrive while the buy was unanswered before the fix, and in issue order after it. `Tradovate_entry_amendment_waits_for_earlier_replies_without_the_reducing_bound` holds a buy's reply, amends an entry limit, then sends a bounded marker cancel: before, the amendment had stopped waiting by then; now it still waits and is sent after the reply.
- **Rithmic.** Not changed: a close reserves the contract as soon as the lane starts it, and `Rithmic_buy_admitted_while_a_close_reserves_the_contract_is_refused` documents that a buy reaching native admission during that reservation is refused and never reaches the venue. [INFERENCE] Only a buy whose asynchronous admission is delayed past the entire close could still be admitted; this predates the lanes.
- **Close position and Reverse** on Binance and Tradovate (`ICoordinatedPositionOperations`) take their send turn when issued and prepare their market order inside it, after the earlier requests were answered. The account's market orders still in flight when it is issued count toward the expected position; Close position cancels working non-market orders (Binance: cancel-all). Only a flat account with nothing in flight sends nothing at once. In its turn the order waits until those market orders have ended and the position includes them (Binance: each order's status read with `GetOrderAsync`, then `positionRisk` or the spot balance; Tradovate: the order has ended and `PositionReflects` holds, that is, its fills are reported and the dated position report is no older than them), at most `NativeSendTurns.ReducingWait` from issue. `NativeSendTurns.PlanPositionOrder` then decides it. Confirmed: the side comes from that position; a close of a position that changed side since issue closes it and says so (`CloseSideChangedMessage`), a reverse sends nothing and says so (`ReverseSideChangedMessage`); flat sends nothing ("No open position."). Unconfirmed: a close sends at most min(best known position, best known plus the signed unfilled quantity of those orders still working) on the best known side, with `UnsettledMessage`; a reverse sends nothing (`NotSentUnsettledMessage`) rather than guess twice the position. Tests (`NativeSendOrderTests`): 1-lot position plus a market buy then Close sells 2 and ends flat, flat plus a buy sells 1; Reverse sells 4 ending short 2, or 2 ending short 1; long 2 with an unanswered sell of 1 then an unconfirmed Close sells 1 (before: 2); an unknown-outcome sell then Reverse sends nothing; a refused in-flight sell of 1 (expected flat at issue) then Close sells 1 and ends flat (before: nothing sent); a refused sell of 2 (expected short at issue) then Close sells 1 and reports the side change (before: "No open position.", still long), Reverse sends nothing with the side change. Accounts Close on Tradovate (`liquidateposition`) has no quantity: Tradovate [cancels the contract's orders and closes the position it holds](https://partner.tradovate.com/api/rest-api-endpoints/orders/liquidate-position) when it processes the request, which the send turn places after the earlier buy's reply; the Accounts test ends flat against a fake venue that liquidates in arrival order, and a refusal (`failureReason`) is raised instead of reported as sent. Rithmic and Bybit keep their own coordinated close; Rithmic Reverse still sizes from the position known when it is issued.
- **Quit drain.** `QuitFlow` and `AppServices` shutdown wait for every gesture already handed to a lane, then (`DrainNativeSendsAsync`) until every Tradovate session's and Binance broker's issued requests were answered (`NativeSendTurns.WhenIdle`), before strategies stop or providers close. Both drains share one deadline, 30 s after the first, so one request that never settles costs 30 s once, not once per drain (`Quit_waits_for_unsettled_native_sends_against_one_deadline` timed out before: the second drain waited a fresh 30 s). While requests are unanswered the status bar shows "Sending queued order requests before quitting…" (a Live notice); reaching the deadline is logged. A gesture issued after that is refused with a visible message, not queued behind the exit. `Quit_sends_a_tradovate_close_queued_behind_an_unanswered_buy…` and `Quit_sends_a_binance_close_that_is_still_reading_the_position…` failed before (shutdown completed first) and pass now.
- **Queued requests are visible.** `INativeSendQueue.QueuedRequests` (Tradovate per account, Binance per broker) counts requests issued behind the oldest unanswered one, from the moment a request takes its turn. A gesture's status adds "· waiting for an earlier reply (N queued)" while it is above zero (safety check: `a gesture's status shows the account's requests still waiting for an earlier reply`; `Tradovate_requests_waiting_for_an_earlier_reply_are_counted_from_issue`).
- **Handed-over turns.** A Close position or Reverse hands the turn it already waited for to the order it planned; that order is not waited for again (`Tradovate_close_behind_an_unanswered_buy_is_sent_after_one_bounded_wait`: before, 3,029 ms with a 1,500 ms bound; now one bound). The order's dispatch claims the turn; until then the position order releases it whatever Submit throws, and a Tradovate order registered for dispatch is dispatched even when publishing it throws (`Tradovate_position_order_whose_submission_throws_does_not_hold_later_requests`: before, a later buy was never sent).
- **Readers never wait on a write.** Moving the call off the UI thread was not enough. With every drive flush slowed to 1.5 s, the safety scene's dispatcher probe still saw one UI-thread wait of 10.6 to 13.5 s (three runs), although no flush ran on the UI thread. `dotnet-stack` samples showed the UI thread in `Monitor.Enter` inside `BinanceBroker.ActiveOrders` (from `ChartTraderPanel.Refresh`), while the lane held the broker gate across `OrderContext.StartDispatch`'s journal writes. Brokers and `OrderContext` hold their gates across durable writes by design, and that is unchanged. Instead, every member the UI reads now uses state published under the gate and never takes it:
  - Binance, Rithmic and Tradovate `ActiveOrders`/`OrdersReady`, and Tradovate `NativeProtection`/`NativeProtectionFault`;
  - the Bybit session's orders, positions, average fill, amendment and unknown-submission flags;
  - `OrderContext.LastError`;
  - `BracketManager` stop, targets, roles, pending attachments, mode and note, which the chart and DOM read every frame. Pending attachments are now returned as copies; `MovePending`/`RemovePending` apply to the manager's attachment for the same entry, so an edit on a lane cannot change a list the renderer is enumerating.

  `UiReadsDuringDurableWriteTests` holds a real durable flush inside each broker's order entry and requires every UI-read member to return within 2 s. On the earlier readers it failed for all four brokers. `BracketReaderTests` holds an account call inside a bracket action, and it failed on the earlier `BracketManager`. All of these tests pass now. Readers see the state published before the write in progress. Bybit publishes at the start of each save, so its readers see the state being committed.
